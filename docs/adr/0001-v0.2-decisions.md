# ADR 0001: Architecture v0.2 decisions

- **Status:** Accepted
- **Date:** 2026-11-18
- **Source:** `docs/tr/architecture.md` (v0.2), review of v0.1

## Context

The v0.1 architecture described a very wide scope for a one-person side project (five adapters, three driver tiers, catalog, MCP, CubeMX, KiCad, networking package). A review covered scope, competition and several technical design issues, and produced the decisions below.

## Decisions

| # | Topic | Decision | Rationale |
| --- | --- | --- | --- |
| 1 | Name | Project **Verino**, CLI `verino` (alias `vrn`), C++ namespace `verino::`. Repository starts at `muskec06/verino` and moves to `verino-dev/verino` when the project matures; links use `verino.dev` | Memorable, scope-neutral; "veri" (data) + verify. Org and domain reserved early so the move is painless |
| 2 | Phase 0 scope | ESP32 + ESP32-S3, two boards, check/render/solve, MCP + skill. ESP32-C3, XIAO, catalog site, `hw detect`, Wokwi and the visual pin picker move to Phase 0b | Make the first product usable within weeks |
| 3 | Phase gates | Each gate has a technical and a usage condition (Gate 0: used in 3 real projects and caught an error) | Don't grow what nobody uses |
| 4 | Zephyr | Deferred, on demand | Zephyr already has a sensor API and devicetree; low return |
| 5 | Positioning | "A verified hardware layer agents don't have to guess about" | Driver count can't compete with PinPilot, espp, esp-idf-lib, SensorLib |
| 6 | espp | First task of Phase 1: compatibility/reuse review (ADR 0002) | `base_peripheral` is very close to `RegisterDevice` |
| 7 | Error model | Sticky error only internally; operations run inside `dev_.transaction()`; public methods always return `Status` / `Result<T>` | "Reads return 0 after an error" produces silent wrong data in agent-written code; enforce by structure, not lint |
| 8 | Capability interface | `sample()` takes one measurement, getters read the cache; names use `caps` (`verino::caps::Temperature`, `caps.temperature` in manifests) | Separate getters triggered separate measurements; three naming styles existed |
| 9 | Behaviour tests | Fake model preferred; replaying a bus trace recorded on real hardware is also accepted | For complex parts a fake model can be harder than the driver |
| 10 | Wrap tier | Wrap esp-idf-lib (BSD/ISC) drivers, labelled "ESP only" | Early catalog breadth; candidates for native drivers |
| 11 | `regs.yaml` | Importable from Rust device-driver YAML via `verino import-regs` | MIT/Apache `*-dd` crates are a ready data source |
| 12 | Publishing | Core + drivers as one package until HAL 1.0. No ESP Component Registry / PlatformIO Registry publishing under a personal namespace | Less release overhead; package names must not break when the repo moves |
| 13 | License | Apache-2.0 | Same as ESP-IDF and Zephyr; patent grant |
| 14 | Solver | Backtracking + scoring | Small pin counts; CP-SAT is an unnecessary dependency |
| 15 | Schematic images | Not in Phase 0; text description, KiCad netlist at end of Phase 1 | Low accuracy, large scope |
| 16 | Language | Strict C++17 subset, not Rust | SDKs are C; Rust replaces SDKs instead of wrapping them; port sources are C++; audience knows C/C++. The gap is on the C/C++ side |
| 17 | Tooling language | Phase 0 tools in Python ≥ 3.11 (`ruamel.yaml`, `jsonschema`, `typer`, `jinja2`, MCP SDK) | Generator and toolchain are Python; YAML comments must survive round-trips |
| 18 | Repository language | Everything in the repository is English, including user-facing messages; Turkish docs live in `docs/tr/` | Global community; a single language for code review |

## Consequences

- Phase 0 is Python tooling only; C++ starts in Phase 1.
- Compat tier, C API and the networking package stay in the design but get no tasks in Phases 0–1.
- Any change to these decisions requires a new ADR.
